# K5d shared numerical parity proposal (2026-11-09)

Status: local implementation and tests only. No source upload, proof, reservation or GPU execution is authorized by this card. The existing exclusive mode remains the default. The separate W8 job remains pinned to its earlier source revision.

The opt-in `k5d-parity16-shared-numerical-v1` retains the original 16-frame native, pixel, metric and judge equality tests. It requests an RTX A6000 with 16,384 MiB plus 8,192 MiB admission margin, shared mode, continue on contention and no resumption. It produces numerical parity evidence only: shared timing, scale and cost are not evidence. PyTorch allocator limits are 8,192 MiB each for the parent and the DCVC child, set before model allocation. Separate retained receipts record each parent and DCVC allocator limit, local PID/process group and pre-allocation state; they do not change numerical comparisons. CUDA contexts, driver and non-PyTorch allocations are outside these limits; the fleet's reactive shared-memory guard and margin remain relevant, so this is not a mathematical total-memory cap. A real bounded smoke must establish fit.

The repository call path is synchronous: the parity parent invokes one CPU wrapper, which invokes a DCVC worker; native encode and decode calls also run serially. These workers inherit the campaign process group. The existing DCVC wrapper contains no direct process spawn. The vendored DCVC source is not present in this local checkout, so its internal process topology has not been independently inspected. Confirm its fixed imported implementation and actual process/device topology before admitting this profile; if a third concurrent CUDA allocator exists, stop. No model, precision, frame count, parameter, numerical threshold or training changes are proposed.

Changed source includes `experiments/tennis/k5d_real_parity.py` and the pre-existing numerical closure member `src/codecs/dcvc_uf_worker.py`; the latter adds only an optional resource guard before model allocation.
