## Findings that change interpretation

1. **The benchmark's saved hand-utility metrics mix encoder and judge implementations.** `experiments/run_comparison.py` defaults `--pose-backend rtm_hand` and extracts the reference `poses` through that backend (lines 163, 198–201, 376), while `evaluation/evaluate_robotics_teleop.py:evaluate_teleop_utility` always runs `extract_video_hand_poses`, i.e. MediaPipe, on each reconstructed PointStream/AV1 video (lines 129–138). `pose_backends.py` documents that RTM hand and MediaPipe are distinct implementations/topologies. Thus the 16 September `comparison_results.json` teleop fields are MediaPipe recon detections scored against RTM-hand reference detections. MPJPE and detection are not a single-implementation comparison. The retained later reports are more informative but also have explicit limits: `offline_gt_report_rtm.json` specifies RTM as GT/evaluator for display, while `eval_split_teleop.py` hardcodes MediaPipe-live as the PointStream wire encoder (lines 58–67, 97–101, 111–132); the report's control-wire MPJPE therefore compares unlike detectors/topologies. `offline_gt_report_wholebody.json` does use the same RTM-wholebody backend for its display-path PS/AV1 outputs, which is a separately useful bounded observation, but still only these three clips and this backend.

   Specific corrected results contradict a uniform superiority claim. Under the saved RTM-hand display report, clip 1 PS 540p is 92.3 px / 66.4% detection vs AV1 540p 103.8 px / 67.2%; clip 2 PS 540p is 68.0 px / 60.7% vs AV1 89.2 px / 68.0%; clip 3 PS 540p is 71.3 px / 65.8% vs AV1 73.2 px / 63.9%. Under RTM-wholebody display, at 540p PS has worse MPJPE than AV1 in clips 1 and 3, but better MPJPE in clip 2 (85.7/70.4/55.9 vs 74.7/82.8/51.7 px); detection changes direction by clip. These are saved observations, not a family-wide result. The pitch's selected legacy table is not a substitute for these backend-explicit artifacts.

2. **The published “oracle ceiling capture” divides unlike denominators.** In `score_pose_tracks`, `detection_rate = matched_hands / gt_hands_total` (lines 49–50, 64–75, 89–92); MPJPE averages only matched hands, so it is detection-conditioned/survivorship-biased (lines 29–31, 80–99). `comparison_results.json`'s `reference_oracle.detection_ceiling` is instead `frames_with_hands / total_frames`, a frame-level nonempty-frame fraction (`run_comparison.py` lines 343–360). `oracle_capture_ratio` is assigned the same value as `detection_rate`; it does not normalize that hand-instance recall by any ceiling. The pitch's 47.6% / 58.0% = 82% and 41.4% / 39.7% = 104% examples therefore compare hand-instance recall to frame-level hand presence, and “104% of ceiling” is not a calibrated measure. The contemporaneous domain note additionally describes “203 out of 300 frames (67.7%)”; the saved JSON has `total_hands: 203`, `frames_with_hands: 164`, `total_frames: 300` (clip 1), so 203 is the number of detected hand instances, not frames. Do not use the 39.7–58% figure as a detector ceiling without reanalysis on a common denominator.

3. **The claimed 47-byte, 3-D control telemetry is not the measured wire path.** `KeypointCompressor.compress_frame` writes a 3-byte packet header, then per hand one flags byte, a 4-byte box and 42 bytes for 21 pairs of x/y coordinates (47 bytes/hand); it discards z. The decoder explicitly fills z with `0.0` (`pipeline/keypoint_compressor.py` lines 23–52, 55–100). At two hands, packet size is 97 bytes/frame including shared header; at 30 fps this is 23.28 kbps before transport headers/loss protection. Actual reported 7.1–10.0 kbps depends on how many hands the detector emits and is just packet-byte arithmetic. More significantly, the main `run_comparison` counts compressed packet lengths (lines 203–206) but feeds original, unroundtripped `poses` to anchor creation and frame synthesis (lines 208–212, 253–266); the displayed reconstruction never decodes those packets. Its visual metrics are therefore not from the quantized wire pose. The public keypoint JSONs are JSON landmarks, not those 47-byte packets. `rtm_encoder_report.json`'s 100% / ~2-pixel “control wire” is a self-roundtrip diagnostic: `reconstruct_rtm_encoder.py` sets `gt = cached_extract(..., "rtm_hand")`, assigns handedness to those GT poses, then roundtrips the same poses (lines 107–112). It is not a measured independent encoder-vs-ground-truth accuracy result. The actual MediaPipe-live wire scored against RTM GT in `offline_gt_report_rtm.json` gives 14.1%, 39.3%, and 19.0% matched-hand detection on the three clips. Preserve the self-roundtrip only as a quantization diagnostic.

4. **The reported “background” includes the original hands.** `BackgroundCodec.mask_hands` defaults to `False` and `run_comparison.py` constructs it without enabling that flag (lines 228–244). `prepare_background_video` then resizes and encodes the unmasked input frame (lines 85–90). Neural hands are later pasted over it, so the AV1 background carries compressed source-hand pixels under/around the synthesized hands; this is not a clean semantic background stream. The separate plate experiment blurs hand boxes. The implementation comment says “blurs/inpaints,” but `mask_out_hands` applies a box blur and selects those pixels; it does no inpainting (`foreground_segmenter.py` lines 95–119). The docs' reported blur experiment may remain an empirical finding for its exact clip/protocol, but does not establish that the main stream excludes foreground pixels.

5. **Main PointStream background “target kbps” labels are not rate caps.** `POINTSTREAM_TIERS` uses labels such as “30k/70k/250k,” but the selected `BackgroundCodec` recipe passes CRF 63; its `target_bitrate_kbps` argument is explicitly unused (`background_codec.py` lines 20–40; `run_comparison.py` lines 49–60, 228–244). The measured saved total rates are PS 69.8–85.9 kbps for “Extreme Starve,” 116.0–144.5 for “Heavy Starve,” and 207.7–276.2 for the 540p tiers. AV1 ladder outputs also need actual rather than target rates: the saved 25 kbps target 180p rungs are 41.7–52.4 kbps and 40 kbps target 240p rungs are 61.9–77.8 (`comparison_results.json`; `encode_av1_ladder.py` measures actual file size/duration at lines 131–145). Pitch tables often do list actual rates, but “target/matched” labels alone do not guarantee equality; compare the saved actual rates rung by rung.

6. **Per-clip byte and rate fields use different anchor denominators.** The JSON says shared anchor = 14,120 bytes, amortized 3.77 kbps over 30 seconds. For each 10-second clip, `run_single_clip_comparison` adds all 14,120 bytes to `total_bytes` but puts only the session-amortized anchor rate in `bitrate_kbps` (`run_comparison.py` lines 214–216, 261–276). Recomputing from `total_bytes` gives clip rates 283.8, 277.9, and 279.0 kbps, versus saved 276.2, 270.4, 271.5: each differs by ~7.5 kbps, exactly the gap between charging a full 14,120-byte anchor per clip and one third of it. Either field can describe a defined allocation, but they do not reconcile as presently named. `shared_anchor_bytes = max(per_clip_anchor_bytes_list)` is justified in a comment as the max being a superset across clips; max of summed per-clip anchors does not establish a union/superset if the anchor sides differ. Also, anchors are rebuilt from each entire evaluation clip and the best-confidence crop per side is retained (`models/dataset.py` lines 108–131); this uses future/reference clip pixels as privileged side information, not a demonstrated causal first-frame handshake.

7. **The headline latency is a component estimate, not a measured end-to-end stream latency.** `latency_profiler.py` assigns SVT-AV1 background encode a constant 13.6 ms (lines 51–54), measures MediaPipe repeatedly on a dummy black frame and the generator on random input (lines 34–43, 61–75), then adds component times (lines 87–109). It does not time encoding/decoding a full input stream, the network, packetization, synchronization, startup, or an operating teleop session. The 18.36 ms parallel and 31.96 ms serial values in the result/pitch are thus a component-sum feasibility estimate for this setup. Separately, the maps sidecars report DWPose extraction p50 255–491 ms/frame (p95 up to 559 ms), incompatible with a sub-50 ms per-frame path; `MapStream.teleop_ok` only checks a serial sum of p50 extraction/pack/codec/decode <50 ms and not bitrate or p95 (`pipeline/maps/contract.py` lines 81–89).

8. **Quality metrics are scoped differently from the headline list.** `QualityEvaluator` returns full-frame PSNR, its simplified grayscale SSIM, LPIPS and DISTS (when installed), plus hand-ROI PSNR/SSIM (`evaluate_quality.py` lines 33–60, 80–138). LPIPS/DISTS use 512x288 resized frames. Hand-ROI scores average crops for detected reference-pose boxes only; missed hands are absent from that metric, and if no crops exist the implementation falls back to the full-frame score. There is no VMAF computation in this class despite README/config listing VMAF. Result provenance does not state metric library versions or perceptual-metric availability. Do not describe these as complete whole-stream task quality or detector-independent hand-region scores.

9. **The maps gallery demonstrates payload encodings, not a validated semantic codec result.** The retained `outputs/maps/index.json` says its clips are 300 frames/10 s from `/home/itec/emanuele/tmp/maps-clips/clip_01.mp4` etc and points payloads/previews to `/home/itec/emanuele/tmp/maps-out`. The 27 retained `outputs/maps/**/sidecar.json` files instead each describe only 48 frames/1.6 s. Example clip 1 YOLOE: index 1,147,528 bytes / 918.0 kbps vs sidecar 184,790 bytes / 924.0 kbps; clip 2 index 285,199 bytes / 228.2 kbps vs sidecar 23,322 bytes / 116.6 kbps, with sidecar `n_skipped=41` and `n_instances=7`; clip 3 index 511,614 bytes / 409.3 kbps vs sidecar 76,075 bytes / 380.4 kbps, with `n_skipped=27`. Canny, DINOv3 and DWPose sidecar payload sizes also differ from index. These are distinct run lengths/results, not one self-consistent bundled output. `outputs/maps/index.json` and `outputs/pitch/maps/index.json` are byte-identical (same sha256 below), so the duplicate does not corroborate the index. Only metadata is in this 133-file snapshot: the referenced native payloads, videos and preview frames are absent. No input file hashes, output payload hashes, model checkpoint hashes, or native encoder versions are saved in the map index/sidecars, so these numbers cannot be tied to exact inputs or reproduced from the copy.

   Within the external-index metadata, DINOv3 int8 features are ~92.3–92.6 **Mbps** (115 MB per 10 s), 1080p Canny is ~8.5–15.6 Mbps, YOLOE RLE is ~0.23–0.92 Mbps, and DWPose keypoints are ~13.7–28.0 kbps with p50 extraction ~303–492 ms/frame. Rate is `payload_bytes * 8 / duration` and explicitly excludes previews (`contract.py` lines 1–4, 77–103). That is native payload accounting, not full transport/wire cost. No saved object-mask accuracy/recall against annotations or task-utility comparison is supplied. The displayed `teleop_ok` bit means only p50 stage-sum latency; it is not a combined low-rate/quality/deployment verdict.

10. **SAM naming overstates the saved evidence.** The 300-frame map index has no `sam31_masks` entries and no SAM sidecars. `pipeline/maps/sam31_masks.py` labels its output SAM 3.1 but explicitly records `SAM_NOTE = "sam3.pt; sam3.1_multiplex.pt not in Models"`, sets `MODELS_KEY = "sam3"`, and loads `ultralytics.SAM(str(weights))`; its predictions are frame-wise and have no temporal IDs (lines 1–12, 41–45, 181–203, 239–264). This code can be described as an unvalidated SAM 3 frame-wise mask path. The separate `sam31_video.py` file has no corresponding saved index/result in the bounded snapshot. Neither file supports a live-demo SAM 3.1 result claim here.

11. **The bounded snapshot cannot verify the interactive page as advertised.** The inventory contains no `interactive_demo.html` or `interactive_report.html`, though README/publish script name these as canonical page inputs (`README.md` lines on “Where numbers and the website live”; `pitch/publish_site.py` lines 3–18, 95–112). No generated `index.html`, preview video, or map preview media is in the 133 files. Therefore this audit assesses the checked-in pitch prose, data index, and publishing code, not the live page's actual displayed labels or the current remote site.
