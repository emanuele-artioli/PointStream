# PointStream code lineage: PR #73–#149

## Scope and method

This record covers the later code lineage in the immutable bare repository `/private/tmp/pointstream-recovery-20260930/source/code.git`, using the captured `refs/heads/pr/N`, `github-prs.json`, and `all-code-commits.json`. For every PR I checked the recorded `merge_commit_sha` and inspected the net tree difference against that merge commit's first parent, rather than treating its title or body as proof of what landed. The accompanying [machine disposition inventory](later-pr-dispositions.json) contains all 77 PRs, exact 40-character PR-head and merge SHAs, base/first-parent identities, net changed paths, disposition, observed diff, and evidence boundary. This section is the interpretation of that inventory and the requested discussion/comment review.

All PRs #73–#149 are marked closed with `merged_at` set in the captured GitHub snapshot. The captured terminal code tip is #149 merge `dcbb4497e214cdccfd525a408f61144c97f0626e` (also `refs/heads/github/main` and `refs/heads/mac/main`; bare `refs/heads/main` preserves a different recovered remote lineage). A PR merge means the code/docs became part of that history; it does not mean its experiment passed or its scientific conclusion survived. The network/raw experiment outputs are generally not in the bare Git repository: several later records refer to `/home/itec/emanuele/pointstream-data/outputs/...`, so I can verify that the repository records those values and protocols, not independently rerun the historical jobs from this source snapshot.

I made no checkout/source changes and started no CUDA work. Negative search results: the PR snapshot contains 149 PR records and all 77 in this range; the only captured discussion bundles requested here are #104, #108, #109, #111. The captured inline review bundle has 19 comments, all anchored to pre-#73 commit IDs; I found no inline comment anchored to a #73–#149 commit. I found no raw campaign result directories in the bare repo (the referenced inputs/outputs are external). These absences describe the supplied recovery set, not GitHub or storage outside it.

## The first “win” and its retraction

PR #73 (`74953ab9902325763cc71d92b402af2df9461c0e`) is a structural documentation change: it creates `docs/areas/*`, findings/PR history/retired-document indexes, a roadmap/setup/session skill and shorter README/AGENTS entry points, while deleting a large legacy plan tree. PR #74 (`0c45b92f2fcbaf8e22192c25b648d85799422ab4`) corrects details in that new operating guidance, including output-root rules and the distinction between per-video encoding and shared-model training. These are documentation/workflow changes, not experimental validations.

PR #75 (`9aecf7037ee8fe9485258dd5e6ffe4a605defa45`) is the substantive codec addition in this phase: VVC and SVT-AV1 background-stream configuration, WebP appearance crops, contract/config plumbing, and tests. PR #76 (`1cf66b4d8ee1a2e905fc4fb527effdc4850654e1`) moves Gate A to the low-rate VVC/WebP configuration and gives VMAF a thread control. PRs #77–81 are measurement/streaming engineering: #77 (`cf1f773b42920a8c58042cbc03549205a7e23f11`) reuses SSIM buffers and adds worker parallelism; #78 (`b74f22736de95f882226a1443a4f762ff060ec27`) fixes the resulting scratch-buffer race by using thread-local buffers; #79 (`8c0105abe76020cf809a4b77b46911762c8339b2`) pipes raw Y4M into VMAF rather than materializing PNG frames; #80 (`5848423dc3b252169b9feaa184aa954a5978a451`) sets VVC `-period 1` for stable causal prefixes; and #81 (`a46df15521ad758246d5d86a78003f51cf18a6de`) streams quality/assembly paths to cut 4K allocations. The reported timing gains apply to metric/runtime work; they do not demonstrate codec RD superiority.

PR #82 (`deceb8d7ea60bdf7f1e8bfc5b36741c3b5a10222`) adds detached codec-pilot/job monitoring with persistent logs and bounded stages. It is operational scaffolding. PR #83 (`2574926bab97abc6f444135636a997930eaa69b2`) records a 192-frame, two-scene 4K Gate A run and declares a competitive “winning territory”; #84 (`fcc76a831d6d8eb094113714769c49e156ab1dbb`) expands that interpretation into comparison tables; #85 (`d4252b5abc0d344a7bd765f8d7551e289b0f9e9e`) adds a frozen procedure and Gate B runner. Those claims must be read through #86, not repeated as current conclusions.

PR #86 (`a3a2570df0a501a6ce09d6531eae5f7fce35cce`) changes the gate checks and explicitly retracts the earlier pass interpretations while keeping reports intact. The recalculation in its docs reports continuous-VVC BD-rate diagnostics of +10.30% for Gate A, +91.30% for the 1080p Gate B source, and +155.22% for the 720p source; it states these sparse-fit diagnostics need sensitivity checks and are not new measurements. The written table has no PointStream/AV1 quality overlap. The #83/#84 comparisons mixed rates and/or quality levels, and the #85 empty-alarm predicate did not actually require competitive comparisons or six matches. Accordingly, neither “below an AV1 bitrate floor” nor a Gate B pass is supported by these artifacts. This is a correction of interpretation and gate logic, not deletion or falsification of the archived raw observations.
