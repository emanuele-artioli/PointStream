This is a proposal, not a run or budget authorization. The 2026-10-31 smoothing cost pilot stopped and its 1,800 CPU-second allocation is closed. No smoothing quality result exists. ## Diagnosis and correction

`experiments/tennis/w6.py` `command_judge` runs `plane_rgb` on CUDA for both original YUV source and decoded paid base, with `dav1d`, four Torch threads, then uses CPU OpenCV DIS, the same `residual_energies`, projection and compositor. `command_flicker_split` explicitly uses CPU for both RGB conversions, selects `dav1d` if available but otherwise `aomdec`, and uses configurable thread count; it shares the downstream residual function. The different RGB path can change integer pixels and hence CPU DIS flow, even though the source YUV hash matches. This is a plausible mechanism, not proof: source energy mismatch does not isolate rounding, library versions or flow nondeterminism. The saved base covers only every third tick and cannot substitute for the full 240-frame sequence.

A concrete correctness defect is independent of that cause: the split records `pass_literal` at 1e-6 and `pass_float32`, but sets `control['pass']` to `pass_float32` and returns exit status from it. A new implementation must gate on **all three literal per-pair checks** (hybrid flicker, hybrid energy, source energy) at 1e-6, with matching valid/NaN masks, and return nonzero on failure. Retain diagnostic fields without assigning scientific pass to a relaxed threshold. This is a proposed code correction; no existing source is modified in this audit.

First reproduce on the same GPU class and exact pinned production environment, code, decoder/version, Torch/OpenCV versions, thread settings and input hashes as the original post job, using the actual `plane_rgb(..., device='cuda')` and original dav1d command. Assert device and intended execution; do not claim bit-exactness in advance. Compare source and base YUV and RGB hashes at representative ticks, then hybrid composition and source-flow hashes, before checking the saved 239 per-pair metrics. The original source YUV hash and saved post archive's recorded `judges.npz` digest are hard gates. Compare all 80 saved GPU-base RGB ticks byte-for-byte and report the maximum difference as a diagnostic; the later correction below records why zero is not a gate for reproducing this historical post. Different decoder, hardware, dependency versions or nondeterministic flow may still prevent literal reproduction. Diagnose first divergent intermediate; if exact historical intermediates or compatible environment are unavailable, stop and report that, not a new tolerance or a reconstructed pass.

GPU class eligibility requires the documented first-model-on-class checks. Do not launch from this document.
5. **Rule and outputs.** Score paired flicker and residual energy over all 239 pairs and player-region LPIPS/DISTS at exactly 80 ticks for baseline, 0.25 and 0.5, with original same-rate SVT reference. A smoothing variant is promising only if mean flicker decreases and neither mean player metric worsens; report paired series/distributions, invalid samples, masks and all three metrics. The design compares one source window only and does not establish unseen generalization, end-to-end superiority or visual realism. The flow implementation and coordinates must be decoder-available, with no source image or annotation fed to the filter.

Consequently zero difference to those cached images is not an identity requirement of the historical post whose temporal arrays we are testing. Retain the full 80-tick comparison and report its maximum difference, including whether it is exactly zero; do not round it or use it to certify the temporal control. The required gates remain the pinned source YUV and saved judge-array hashes and the original per-pair 1e-6 comparisons for all three arrays with identical NaN masks. The new control uses the production CUDA conversion and four Torch threads within one inherited CPU affinity; OpenCV runs with one thread and the historical base decoder was invoked with two.
