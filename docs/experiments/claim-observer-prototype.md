# Task-specific claim observer

This is a review candidate, not a released fleet component. It does not submit, retry, signal another process, release claims, execute inference, or measure physical GPU use. It is scoped to one gpu6 exclusive one-core request. Use requires separate source review, a CPU-only host pilot, and root approval; it does not repair the missing historical 13aba release timestamp.

Invoke `python -m experiments.jobs.claim_observer CONFIG OUTPUT`, where OUTPUT is a new directory on a separately mounted local ext4/xfs/btrfs filesystem and the atomic binding file also lives on local storage. CONFIG supplies `host` (gpu6), `host_fqdn`, `gpu_uuid`, `nonce`, canonical `spec_sha256`, `source_sha256`, canonical digest of spec inputs as `inputs_sha256`, `control_sha256` mapping installed absolute file paths to hashes, `gpu_claim` (exact exclusive claim.json path), `cpu_claim` (host allocation JSON), `inbox`, `binding_file`, `max_samples`, `poll_seconds` (>=2), `read_timeout_seconds` (0<value<=10), `max_gap_ns` and `cpu_seconds`. Pin and independently audit the whole config before use; do not allow arbitrary participant selection. The process requires one-core affinity, restricts the loop duration conservatively to at most 45 minutes, hashes installed controls in a bounded child, then fsyncs `ready` and `ready_complete` journal records before publication. Root must independently establish the READY record was durably observed before the one submission. After the canonical submit returns, atomically write a binding file on the same local host containing the matching `nonce`, `job_id`, `spec_sha256`, `source_sha256`, and `inputs_sha256`. A missing, changed, late or ambiguous binding fails closed. The observer never searches the inbox for candidates.

The observer records samples in `journal.jsonl` and a final result; validate independently with `python -m experiments.jobs.claim_observer --validate OUTPUT/journal.jsonl`. A bound result requires a prior absent device-claim sample, an observed exact job/token claim, joined live campaign and supervisor PID/birth records, one-core CPU token observed present, later token disappearance, terminal state, CPU-token absence and absent original group/supervisor. The read completion of the last necessary sample is the conservative end of the reservation bound. A missed claim, gap, read error, absent final record, changed job identity, inconsistent token or missing teardown evidence is unknown. SHA256 token digests, not token bytes, are retained.

NFS attribute caching, transient acquisition states, stale data, clock skew/jumps between publication and observer, PID visibility/permissions and control-release identity must be independently qualified. The observer cannot prove NFS coherency and a bounded result is conditional on it. Wall time is used solely for prepublication ordering; elapsed bounds use same-boot monotonic timestamps. Child CPU accounting is cumulative `RUSAGE_CHILDREN`, recorded separately from the observer and guarded along with the parent's CPU. Each NFS read runs in a separately bounded child; a stuck uninterruptible reader yields unknown and can require operator inspection. Root must account manager, submission, storage, audit and any observer CPU separately, and must not infer actual GPU use from reservation time. Receipt corruption or a crash without a durable final row is unknown.

A prospective no-GPU pilot should use owned synthetic byte-only local claim/spec fixtures with real schema, controlled claim transitions and a known NFS visibility check; freeze actual sample count, reader timeout, CPU and wall caps before release. There is no measured CPU forecast yet: `max_samples × (poll_seconds + read_timeout_seconds + 4)` is a conservative configured wall cap, not CPU time. No Linux/fleet pilot has run.
