# Low-rate ball signal at an equal total budget

The ball-machine figure asks whether the 63.0575 kbps full-frame baseline can retain the benefit of a streak when the base is reduced enough to pay for the ball signal. Use the original TrackNet game9/Clip5 and the existing SVT CRF62 packet and rendered-ball payload from job 20261113T173340Z-64160888. The source is 292 frames at 30 fps, with 261 visible, 30 absent and one uncertain label.

Hypothesis: reallocating ~1 kbps to the already fitted streak retains most of the earlier 5-to-229 visible-frame detection improvement at the baseline's total 63.0575 kbps. The competing explanation is that the reduced base changes the detector or makes the preexisting streak a poor fit. This is a fixed-sidecar first pilot; it holds the saved sender trajectory and fitted appearance constant. A separately registered refit can measure adaptation to the changed base. It uses no source labels to change the track.

The first CPU-only step reopens and verifies the saved packets and source, re-encodes the base with the same pinned SVT 4.2 codec and seeks an actual packet within 0.5% of the original no-ball baseline, searching CRF between 62 and 63 with up to six steps. Every point's actual stream and total packet bytes are recorded. Smoke uses 24 source frames and the same native encoding and packet path at 62 and 63; its duration and exact identity gate the full 292-frame run. Verify nonempty outputs, frame count, source and payload continuity, deterministic receiver rendering inputs, and exact 292-tick rate accounting. If no point meets the rate tolerance, keep the trial table and the two bracketing packets without calling it matched. Charge packet headers, the entire native stream, all symbols and all 292 frames. Do not pad.

The derived packet will next be scored by the frozen WASB checkpoint on decoded RGB only, alongside the original baseline. Count independently labeled visible hits at 10 and 5 pixels and absent-frame false positives. Separately rejudge the saved original streak RGB to establish runtime parity. Count false placements and misses, report whole-frame change and retain the historical 64.0849 kbps streak as another comparator. The historical reference is a retrospective development clip. A matched result on this clip is a pilot for a new-match confirmation, rather than a multi-match claim.

Budget for this CPU step: at most 1,500 wall/CPU-seconds, one CPU, zero GPU. The packed environment, original 2.4 GB source archive and 3.5 GB published artifact are hash-identified and stage to host-local disk. Smoke and full deadlines are within 45 minutes. Full promotion requires a passing smoke and a conservative observed runtime projection with 1.5× margin. The independent detector is a separate GPU-budgeted job and is not authorized by this CPU request.

## Refitting the sender's appearance

The original sender's source-only BallTrack predictions are archived frame by frame in the prior source-qualification record. The proposed [CPU refit worker](../../../experiments/tennis/ball_matched_low_refit.py) converts those predictions to the existing sender's rounded/clamped track and runs the production streak fitter against both the original and newly rate-matched decoded bases. It uses the source image and the saved model predictions for fitting, with no source labels as input to the fitter. Its full-stage reproduction gate requires that the original base reproduce the exact saved original streak payload, which checks that the retrieved predictions and fitting path match the archived sender. The new fit is separately priced, and its actual packet must itself satisfy the rate criterion before being described as a matched-rate point. Source labels are reserved for a later independent detector comparison.

The first CPU run intentionally freezes the original appearance to test the effect of reallocating bits alone. If native VBR finds a matching packet, a bounded refit and its parity gate can be staged from the same immutable artifacts.
