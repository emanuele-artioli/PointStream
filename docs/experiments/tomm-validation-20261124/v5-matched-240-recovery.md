## Decision and scope

On the frozen Shanghai match102 240-tick excerpt, compare both paid player roles with `ddim30_512_ov4` and `dpm10_512_ov8_smooth` from `tomm_v5_pareto_pilot.py`. Compare sums of CUDA-synchronized render time across exactly the same roles and tick ranges, separately report each role, model load, and other wall time; only call the comparison exclusive if the fleet receipt confirms no contention. The treatment changes sampler, steps, overlap and pose smoothing together, so it cannot attribute any change to an individual factor. The speed result is for these inputs and the qualified hardware and implementation only; do not infer full system end-to-end latency from render time.

Hypothesis: the combined DPM-10/smoothing configuration renders faster than DDIM-30 on the matched two-player scope. Competing explanations include shared-GPU contention in prior measurements, different context boundary overhead, model initialization, and frame-dependent runtime. A result with missing, repeated or mismatched ticks, different device model or unverified exclusivity does not answer this question. Also report quality and temporal behavior separately if scored; elapsed time alone does not establish a quality-preserving speedup. No numeric decision threshold is preregistered in the prior evidence, so report the measured ratio and uncertainty/limitations without inventing a pass threshold.

## What the saved evidence permits

The shared Ada V5 stabilization receipt `20261124T121722Z-89fd9610` records 48 frames per role: DDIM totals 674.47 s and DPM/smoothing totals 206.51 s, both `timing_contaminated: true` ([receipt](v5-stab-summary.json)). Five times these numbers is about 3,372 s and 1,033 s respectively, or 4,405 s render time before loading, staging, smoke, validation and archival. This is an illustrative linear extrapolation, not an exclusive-runtime forecast: a single 240-frame pipeline call may scale differently or exhaust memory. It already exceeds both the old spec's 1,800 s full-stage limit and 2,400 s total budget, and a single stage waited on must end within 45 minutes. Do not change the old 8/48 guards or submit a 240-frame spec with these bounds.

## Recovery design and required implementation

A possible bounded design is five separately saved 48-tick segments, `[0,48)`, `[48,96)`, `[96,144)`, `[144,192)`, `[192,240)`, each containing both roles and both configurations. This changes the generated sequence relative to one uninterrupted 240-frame call: context scheduling and random draws restart at segment boundaries. It therefore measures **segmented 48-frame generation**, not an uninterrupted 240-frame decode. Smooth the complete 240-frame pose sequence before slicing, otherwise the smoothing rule itself changes at each boundary. Do not report stitched visual/temporal quality as the continuous decoder's quality without evaluating boundary effects. Check the input packet actually has identical intended 240 ticks and both roles before treating these indexes as valid.

Before this can run, implement explicit segment selection, retain existing 8/48 behavior, and design reproducible segment seeds and per-segment output names. Save each completed segment through the fleet's supported publication/checkpoint mechanism; saving only in job-local scratch does not survive a failed job. Verify the pinned pipeline's context behavior and GPU memory on a representative smoke before accepting segmentation. The validator must verify all expected `(segment, role, config)` combinations exactly once, ordered tick identities and count, finite positive synchronized times, GPU/device and exclusivity receipts, config and input identities, archive hashes and actual per-record artifact contents. Reject partial, duplicated, contaminated or mismatched results. Aggregate only after all five segments pass, on the same qualified GPU model and configuration, and report the segmentation and each job ID, revision, environment, inputs and patch checksums.

The existing validator only checks nonempty records, frame counts, frame distinctness and positive times; its smoke exercises only the first role and filters a fixed configuration set. It is insufficient to validate the proposed paired complete cohort. The existing driver also hardcodes 8/48, processes the prefix only, and writes its summary/archive after all configurations finish. Simply changing the allowed frame count or splicing its outputs would therefore give misleading coverage or unsafe recovery.

For any future implementation, first inspect existing fleet jobs and all eligible hosts, check the model–GPU qualification table and select one qualified model for every segment, verify the archived input and environment hashes in the existing exclusive spec, and record a new absolute deadline and the aggregate GPU-time budget within the authorized cap. Include all five smoke stages, staging, validation and retries in the budget, and stop when the authorized budget or deadline cannot cover the remaining work. A GPU smoke is infrastructure validation, not timing evidence; its first-model-on-class checks must cover the intended GPU and kernels. Use `scripts/ps-fleet wait` within its 45-minute bound. The existing SHA-identified carrier, base and weights are historical identities, not proof that the files are currently accessible or still match.
