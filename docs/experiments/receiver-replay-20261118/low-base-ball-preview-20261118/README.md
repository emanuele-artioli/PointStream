# Ball on the original lower-rate receiver

The original player-only receiver used a 480×272 conventional base, the two generated players and their masks. This preview adds the same 32×32 paid ball channel at the 195 available trajectory positions. The other 45 frames pass through unchanged. The base retains the original foreground outside the masks. The original source digest is `b7d887c0e2ba15ecc4f6e831d23942b2eb0857e40385c840ea4249d037433f1d`, as recorded in the existing rate-support and review receipts. The source MP4 was not rehashed for this preview.

The 391,798-byte player carrier and 625-byte receiver manifest total 392,423 bytes, or 654.04 kbps. The rebound ball sidecar costs 19,114 bytes. The joint total is **411,537 bytes, or 685.90 kbps** for 4.8 seconds. Display H.264 is a separately encoded viewing copy. This is an offline ball overlay on the audited receiver output.

`prepare.py` authenticates and opens the existing sidecar, binds it to the original player carrier, round-trips it and checks the decoded ball tile stream hash. `render.py` runs on CPU next to the saved receiver archive, checks all 240 pre-ball frame hashes against the independent finish audit, checks unchanged pixels outside the ball tile, and verifies the 45 absent frames. The first render attempt stopped at tick zero because it used a plain byte hash instead of the independent audit's dtype-and-shape-prefixed array hash. It left a separate incomplete video. The corrected attempt checked all 240 ticks, used 13.60 CPU-seconds, and produced a 1920×1080, 50 fps, 240-frame video. The transferred video hash matches the campus receipt. No GPU was used.
