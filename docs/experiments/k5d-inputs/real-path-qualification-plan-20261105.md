This is circular. A separately reviewed confirmation gate must allow **only** those two registered clips, a fixed sequence and independently reconciled inclusive job caps, without approving or weakening the full-study gate. 2. `k5d_cpu_accounting.measure` is a subreaper and its timeout kills a process group. It does not contain descendants that create a new session. The synthetic namespace launcher deliberately rejects actual workloads and CUDA; neither it nor the fleet's ordinary process-group termination qualifies the proposed combined path. Nested user/PID namespace permissions, normal completion, interruption, descendant cleanup and CPU counter completeness must be observed on the actual host. A launcher disappearing is insufficient proof that native tools or CUDA descendants disappeared. Resource usage must be independently checked and must not treat elapsed wall as measured CPU consumption. Staging, validation, supervisor and audit remain separate charges.
3. The old H3 manifest bridge covers eight additions and is explicitly unapproved; current `CONTROL_ADDITIONS` names fourteen. It cannot be used as a bridge for the present tree. Build a fresh, immutable, selected source snapshot from the calibration archive with only individually reviewed orchestration/proof additions; compare the *complete* archived manifests and environment hashes, prove all old files including codec, pixel, metric and judge modules byte-identical, and bind both exact actual dispatch identities. Never relabel a historical checkpoint. The consumer producer and scorer must use each other's actual identity.
4. CPU readiness `e9104e5e` establishes only warm-cached header/label/checkpoint checking, not full production cost, decoded pixels or CUDA. The programme's CPU fit and cold staging costs remain unproven. A hard prospective CPU allowance needs an enforceable process-tree bound and separate lifecycle allowances; one-core wall time alone is not an observed CPU counter or proof that children cannot escape the allocation.
