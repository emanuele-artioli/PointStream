# Experiments: player conditioning requalification

### 2026-11-16 — source audit and future-fit correction

**Finding and change.** The pinned long-video inference pipeline forms its CLIP input by calling `ref_image.resize((224, 224))` on an RGB PIL image before `CLIPImageProcessor` (PIL's default RGB resampling is bicubic). The old `k6b_fit.encode` passed each 512×784 array directly to the processor; its standard shortest-edge resize and center crop therefore see a different field of view. Future fits now use the inference resize first. This changes the default training recipe and its code identity: existing fits and their receipts retain the old source and weights, and are not repaired or requalified by this change. The upstream training dataset also sends its original reference directly through CLIP; this change aligns PointStream fitting with **its long-video inference**, not a claim of identical upstream training. This discrepancy alone does not explain generic generator quality or show historical fits failed.

**Source and scope.** Read the public fork `emanuele-artioli/Moore-AnimateAnyone` at `67c42297f8024ddb0fd04b69e42ac71fe6bbf3d8`, the documented fork of MooreThreads `a914ef3`. Retrieved the commit by a read-only clone to temporary storage. `animate_anyone/dwpose/util.py` SHA256 `6eb8effe3ac50d31ea3140c0d084b04f099c2a0fecc9da53c4f6cf27cd186f4f`; `animate_anyone/pipelines/pipeline_pose2vid_long.py` SHA256 `480971c58c845c8636a9b0e616708f07bd7d7a5c19ae3c20b9439c0c9ac90a7f`. The local source clone is not the historical archive; the archive itself was not checked. Dependencies documented in `docs/resources.md` are diffusers 0.30.3, Pillow 12.3.0 and transformers 4.57.2 in the archived lock. No model, dataset or historical result was changed.

**CPU observations.** An asymmetric red-top/blue-bottom RGB fixture confirms the new pre-CLIP PIL image is 224×224, keeps both ends, preserves RGB, and uses the same PIL resize invocation as the long pipeline. This checks the input to the processor, not its actual output tensor or GPU embedding. The fork's inference reference VAE processor converts RGB and normalizes to [-1,1], while PointStream fitting uses NCHW float `/127.5 - 1`; its inference pose processor converts RGB without normalization beyond [0,1], matching fitting's NCHW `/255`. These are code-path observations; the exact pinned processor tensors have not been run side by side. Fitting samples VAE latents, while inference uses the reference mean; fitting is single-frame and inference uses the temporal module. The fork's image-sequence dataset has its own augmentation and CLIP preprocessing; PointStream fitting is not an exact replay of that native recipe.

A synthetic COCO-17 body, including an invisible elbow, was passed through PointStream's conversion and both the actual pinned upstream body renderer and `pose_map`; on the local CPU environment, 54 of 401,408 pixels differ. The upstream normalizes coordinates and multiplies back before integer truncation; floating-point roundoff may shift raster edges. This comparison adapts the same visible body points to the external renderer and does not validate native DWPose detection, confidence decisions, hands, face, or the full native image preprocessing. It is not evidence that the drawing difference caused a model failure. The test imports and hashes the actual upstream util when `POINTSTREAM_AA_UTIL` names that file; otherwise it skips that external comparison.

The synthetic geometry check covers a fractional, partly out-of-frame box: `int_box` rounding is shared by image crop and keypoint transformation, zero padding is on the expected side, and RGB survives. Resampling uses pixel centers, so the transformed integer keypoint marks a source pixel's edge, not its center. In preparation, fitting uses uncoded pose and source RGB while generation uses coded pose boxes and a source-RGB reference with an uncoded-pose box. These are different conditioning distributions; this synthetic fixture does not verify actual manifests, frame alignment, coded/source dimensions, clipping frequencies, or target coverage.

**Release boundary.** CPU checks do not establish end-to-end tensor or GPU parity and do not requalify historical results. Before a new GPU comparison, use a predeclared, budgeted short correctness smoke with exact environment and source/checkpoint identities: compare the actual pinned CLIP and VAE/pose processor tensors (shape, RGB order, values and resampling) for the same asymmetric reference and pose; check coded/source frame sizes and timestamp/box joins on the selected real records; verify device, dtype, motion and attention paths; then render a short fixed sequence and check complete finite, non-flat output and recorded conditioning hashes. Treat historical and corrected fit recipes as separate methods. No GPU run or training was authorized or performed here.
