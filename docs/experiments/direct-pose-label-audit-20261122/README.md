# Direct body-pose label audit

The proposed paper figure asks whether PointStream's delivered 17-joint player points support a machine task directly at a bitrate where decoded video degrades. The comparison must use human-labeled source-frame joints, not the pose encoder's own output as truth; showing feature availability alone does not establish accuracy or a machine advantage.

## Available and missing inputs

The authenticated Nadal–Kyrgios /000 240-frame, 50-fps development rally has actual paid KPS player packets and complete receiver reconstructions (see `docs/experiments/joint-trajectory-20261122/README.md`). Existing source-reviewed body masks and the original frozen ticks 10, 30, …, 230 support the existing body-fidelity comparison; they are silhouettes, not human-annotated joint positions. The same source has real starved ordinary AV1 and accepted native QP5 DCVC-UF output; `docs/experiments/starved-dcvc-regions-20261122/README.md` records its independent source/decoded-frame identity gates. The available RacketVision inventory explicitly describes *racket* box and five racket landmark labels, ball labels and no body-pose class. The 5 racket keypoints are not human 17-joint skeletons. Project reports using RTMPose or other model predictions compare against another model, not independent annotation (`docs/experiments/submission-ladder-player-demo-audit-20261115.md`). No authenticated independent human body-joint labels for these exact packet-aligned source frames were located in the repository experiment records or campus dataset manifest inventory. This is a bounded search, not proof that no external labeled source exists. Do not score predicted joints as ground truth.

## Smallest decisive annotation add-on

Freeze the existing 12 ticks 10, 30, …, 230 of this already opened rally, both visible players (up to 24 person-frames), before looking at any decoded/model pose outputs. Independently mark source-image coordinates and visibility/occlusion for the standard 17 human joints; label each actor identity and source-frame ID, and record unavailable/ambiguous joints instead of guessing. This is at most 408 joint slots, fewer if obscured; it is a feasibility pilot, not a population estimate. Verify original video SHA, full-resolution geometry and native 50-fps tick identities. Use source-only annotations blinded to codec and pointstream predictions, with an independently reviewed subset and a frozen coordinate/visibility convention. Annotation work is not already done.

Then read the existing decoded/transmitted player KPS at the identical ticks and actor identities. Compare them with one fixed independent pose model run on actual ordinary AV1 decodes at or below the joint mode's actual rate, and, where available at the same rate ceiling, the accepted DCVC-UF decode. Run the same model on source RGB as a reference ceiling and optionally on actual PointStream RGB; report every actor/joint match, misses, false persons, visible and occluded counts and missing transmitted joints. Freeze model, threshold, matching and normalization before outcomes; verify its training lineage excludes evaluated frames. Record the actual full bitrate, reference/adapter reuse assumption, exact source/packet/decoded hashes, all frame times and transformation from coded to source geometry. Compare direct KPS vs the model's decoded-frame estimates on the same human-visible joints, using normalized per-joint error and a prespecified correct-within-tolerance recall, with person matching performed without using predicted correctness. Do not fill missing joints from human labels or claim detector-training independence without evidence. Analyze near/far players separately as descriptive sensitivity, and expand across new matches before making a general VCM or population claim. This small pilot does not require a new renderer and should not displace the independent-match joint receiver.
