# PointStream paper figures

PointStream splits a broadcast at scene cuts. On suitable shots, the sender can describe foreground motion with points and transmit appearance where needed. Other shots use a conventional codec. The research question is which representation makes the best use of a given bandwidth budget for a viewer or a machine. Keep system design general. Tennis provides the principal evaluation.

## Argument for the rewrite

A video application may need both the image of an action and the position of the object involved. PointStream can send them together. Open on the same rally at 20 kbps: the viewer can see the reconstructed ball, and a machine can read the trajectory from those same bytes. Then ask when the sender should draw the object, send its pixels, or keep the ordinary video and send only its position. Tennis makes these choices measurable. Pose-conditioned players raise a second question about paying for appearance when the broadcast returns to the same people.

The last submission emphasized a 7–10× bandwidth reduction with an ultrafast HEVC anchor and advance model delivery. The reviews asked for stronger codecs, an account of what the receiver already knows, and evidence about motion and changing views. Use the present AV1, ROI, DCVC, in-motion and continuous-broadcast comparisons to answer those questions where the measurements are comparable. Introduce Lai et al.’s earlier tennis scene decomposition and coordinate map alongside the first system figure. Distinguish PointStream through the reconstructed broadcast, direct machine access and the measured cost of supplying both outputs. ## Manuscript sequence and figure priority

Lead evaluation with **two separate rate–quality figures**, one for all players and one for the ball. Put total delivered bitrate on x and the same regional metric on y. Target 20, 50 and 125 kbps, plot actual rates, and preserve higher-rate outcomes to show the boundary of any gain. Use only the common measured support when pooling curves. Average people within a shot, shots within a match, then weight physical matches equally; for historical union-mask scores preserve their original regional definition. Show match observations and training exposure. Use a near/far split as a diagnostic only if a prespecified scale effect persists across matches. Do not pick a different winning rate for each test match.

## Twelve-hour run order

The November 21–22 campaign runs from 21:24 to 09:24 UTC on campus. The order below gives each figure’s decision and evidence. The receipt for each run records its shorter limit.

1. **Measure foreground at a real low price.** The [combined-receiver trial](docs/experiments/joint-trajectory-20261122/README.md) puts both bodies and the ball on the same 4.8-second display at 21.545 kbps with valid references, or 428.777 kbps from startup. Compare six spatial-resolution/ROI controls and a separately qualified 12-tick DCVC control where available. The three-phase serve image uses exactly the stream in the rate plot.
2. **Check what generalizes.** Compare the [nine player windows](docs/experiments/player-rd-historical-20261122/README.md) and the three opened ball windows, keeping both people together in the player score. Report common-rate player coverage and omit unbracketed curves from pooled points. [Basel](docs/experiments/ball-basel-confirmation-20261122/README.md) is the prespecified fourth-match test of tracked ball pixels. [Different-match joint replication](docs/experiments/joint-replication-feasibility-20261122/README.md) needs compatible full-cadence inputs and independent labels for both classes.
3. **Measure what a machine receives.** The [dense ball test](docs/experiments/ball-matched-low-20261122/README.md) measures both visible-frame hits and absent-frame errors. On [Adelaide](docs/experiments/ball-adelaide-prospective-20261122/README.md), the prospectively chosen video-plus-coordinates mode leaves every ordinary video frame unchanged. Keep player-mask IoU and pose coding error in the supporting material.
4. **Charge both court visits and the gap.** Use the [indexed two-rally receiver](docs/experiments/cumulative-joint-20261122/README.md), an [identical-gap conventional comparison](docs/experiments/passage-same-gap-20261122/README.md), and [continuous AV1](docs/experiments/passage-native-20261122/README.md). Check the actual displayed return after charging the initial state. The [routing figure](docs/experiments/passage-routing-20261122/README.md) identifies where the retrospective replay differs from the deployed selector.
5. **Use appearance and background tests to explain the mode choice.** The [shared reference review](docs/experiments/common-reference-q78-20261122/README.md), [Q90 pilot](docs/experiments/common-reference-q90-20261122/README.md) and [real cache return](docs/experiments/cross-shot-reference-20261122/README.md) answer different questions. The [reference-cost figure](docs/paper/figures/system/joint-price.pdf) prices a specific ongoing mode over active use. Compare donor filling with inpainting when the source permits ground-truth scoring. Keep detailed image-codec ladders and distorted equipment examples in the appendix.

The 21.545 kbps joint serve now has three compatible anchor families: ordinary AV1, effective regional AV1, and independently decoded DCVC-UF. At 20.450 kbps the neural stream gives 0.3924 body and 0.3439 ball DISTS versus 0.2617 and 0.3450 for the cached joint stream. Show the neural point wherever this comparison is introduced. Against ordinary AV1 at 21.623 kbps, PointStream improves both object regions while giving up 2.85 dB of full-picture RGB PSNR. Put the body motion-error result beside the serve clip. ## Working from figures

For a paper experiment, name the panel and draft its caption first. Specify the missing row or point, metric and denominator, rate accounting, comparator and the decision the result would change. Look up existing receipts before running anything. Add the new result, including an unfavorable result, to that panel’s evidence file and regenerate its figure. Experiment records own detailed methods, job IDs and budgets; this page owns the order of work.
